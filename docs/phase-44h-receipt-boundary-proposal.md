# Phase 44H proposal: an authoritative action-receipt boundary for robot, email and calendar actions (for review, 2026-10-10)

Status: **architecture proposal only.** No code, no migration, no change to the live response path or to any authorization, consent or confirmation mechanism. It builds on the [Phase 44H investigation](phase-44h.md) (regression case H-001, the prototype claim detector) and [ADR 0028](adr/0028-persona-responses-and-action-receipts.md) (receipts are built from persisted state, never from reply wording). Decisions belong to the owner; section 9 lists them.

## 1. Problem and goal

A model-generated reply can say that a consequential action succeeded when nothing happened (H-001: "The robot is now asleep."). The goal is a boundary with one rule: **text may describe system truth but never define it**. A success statement about a robot, email or calendar action may reach the owner only as a rendering of an authoritative receipt, in a state that supports the words used. The boundary must not decide whether an action is *allowed*; that stays where it is today.

## 2. What exists today (verified in the code, 2026-10-10)

| Domain | How the action happens | What is recorded | Gaps for a boundary |
|---|---|---|---|
| **Robot** | Owner commands (`/reachy standby`, `/reachy wake`, behaviours) reach the hub (`POST /robots/standby`, `/robots/resume`, `/robots/{id}/behaviour/{name}`, `require_remote_auth`), which calls the embodiment service, which calls the daemon. Unattended exceptions (wake/sleep animation, alarm sweep) run inside the embodiment service. | The hub returns per-robot `{ok, ...}` or `{ok: false, error}` to the caller. **Nothing is persisted.** No receipt type exists. | Success is the HTTP status of a command, not a read-back of the daemon state; an unreachable robot after a sent command is indistinguishable from "did not happen"; unattended motions leave no record. |
| **Email** | Draft, then approve, then queue (`dispatch_at` ten minutes ahead, ADR 0011), then the dispatch loop sends through SMTP and `mark_sent`. Cancel reverts QUEUED to APPROVED. | The draft's own status (`draft, approved, queued, sent, cancelled, rejected`) and timestamps. **No receipt.** A send that raises is logged and retried on the next pass; there is no `failed` or `unverified` state. | An SMTP timeout after the server accepted the message could cause a duplicate send; "queued" and "sent" are not separate from the owner's point of view in any receipt. |
| **Calendar** | The agent has read-only access (next, list, free-busy). Events enter through the operator API (`POST /calendar/events`) or provider sync; provider writes are "later, behind confirmation" (ADR 0010/0011). | The stored event. No receipt. | Nothing to claim today, but a future write path must not start without a receipt contract. |
| **Planner, tasks, alarms, memory** | Deterministic handlers. | `ActionReceipt` rows (migration 018): `alarm.created|cancelled|delivered`, `reminder.created`, `task.created|completed`, `memory.created`, `deep_review.*`; `status` is `success` or `failed`. | Two states only; no pending or unverified; receipts are written by core only. |

## 3. Outcome states

Receipts record **what the system can vouch for**, with four outcomes (plus the initial request):

| State | Meaning | Examples | Words a reply may use |
|---|---|---|---|
| **completed** | The owning service has an authoritative confirmation that the effect holds. | SMTP accepted the message; the daemon reports the sleep pose on read-back; the calendar provider returned the event id. | "Done", "sent", "is now asleep", "added". |
| **failed** | The effect definitely did not happen, with a reason category. | Policy refused; robot reported an error; permanent SMTP rejection; provider 4xx. | "That didn't work: <fixed reason>". |
| **pending** | Accepted and expected to take effect, but not effective yet, and still cancellable where the design says so. | Email QUEUED until `dispatch_at`; a robot motion accepted and in progress; a provider write awaiting acknowledgement. | "Queued, it will be sent at 10:12 unless you cancel", "starting now". Never "sent" or "done". |
| **unverified** | The command was sent or may have taken effect but the system cannot confirm either way. | SMTP connection dropped after the data was sent; robot unreachable after the command left the hub; daemon read-back timed out. | "I asked; I can't confirm it happened". Never "done" and never "failed". |

Transitions are **append-only events** (a new row that supersedes the earlier one), never an edit: pending to completed, failed or unverified; unverified to completed or failed when a later check resolves it (for example the next heartbeat shows the pose). The reply layer reads the newest event of an attempt.

## 4. Receipt shape (additive to `ActionReceipt`)

`correlation_id` (one id per attempted action, generated by the owning service, also carried on the request that caused it, so a turn can find its receipts), `supersedes` (previous event id), `outcome` (the four states), `action_type` (new families `robot.*`, `email.*`, `calendar.*`), `object_type/object_id` (draft id, robot id, event id), `source_channel`, `at`, concise string `fields` (no body, subject, recipient address, transcript or prompt: ids and labels only, as today), `failure_reason` (category), and `verified_by` (`ack`, `readback`, `none`). Existing `status` stays and maps `success` to completed and `failed` to failed, so current receipts, the Telegram renderer and the Activity tab keep working.

## 5. Who writes receipts and where they live

- **Rule:** the service that owns the effect writes the receipt, at the moment it learns the outcome: the hub for robot commands, core for email dispatch and calendar, embodiment for unattended motions (reported through the hub). **Never** companion-core's reply layer, never a model, never a tool result echoed by a model.
- **Storage:** one authoritative table, the existing `action_receipts` in core (it already feeds Telegram and the operator UI). Hub and embodiment submit through a narrow service-authenticated route in core (for example `POST /receipts/report`), which accepts only an allowlist of action types and outcomes from the calling service identity, rejects a receipt for an action the caller does not own, and is idempotent on `(correlation_id, outcome)`. This keeps services communicating over HTTP (ADR 0001) and adds no sibling imports. The alternative, a hub-local receipts table, is simpler but splits the truth the boundary must read; not recommended.
- **No input path for authorization:** receipts are read by the reply renderer and the UI only. No consent gate, command parser, route guard or tool call may take a receipt as proof of permission.

## 6. The reply boundary

1. Deterministic handlers keep producing fixed replies; they would gain the outcome vocabulary for pending, failed and unverified, and keep their receipts.
2. Any reply produced by a model passes a **claim check** before release (the prototype in `aq/assertions.py` is the measurement tool): each sentence that asserts a completed consequential action must be backed by a receipt of the matching family with outcome `completed` from the same turn (matched by `correlation_id`, not by time). Claims of "queued", "starting" need `pending`; "tried" needs `unverified`.
3. An unbacked claim sentence is **replaced by a fixed correction** ("I didn't do that. I can't do that from here.") and counted. A model is never asked to repair it. In the generic branch no tool exists, so every action claim is unbacked by construction.
4. Longer term, the strongest form is to **render every consequential confirmation only from receipts** and let a model supply tone around it, not the fact.
5. The check cannot be perfect on free text (recall 0.88 on the labelled set; passive and indirect phrasings slip), so it reduces risk and is paired with the structural rule in item 4 and with the action-boundary instruction.

## 7. Domain mapping (what would be recorded)

| Action | Receipt events | `completed` requires | `failed` when | `unverified` when |
|---|---|---|---|---|
| Robot standby or resume | `robot.standby`/`robot.resume`: pending on command acceptance, then completed/failed | daemon state read-back matches (the hub already reads daemon state for status) | daemon error state, refusal, HTTP error with a response | the robot is unreachable after the command left, or the read-back times out |
| Behaviour playback | `robot.behaviour` (name label only) | embodiment reports the move finished | embodiment reports an error or refusal | connection lost mid-move |
| Unattended wake/sleep animation, alarm sweep | `robot.animation`, `alarm.sweep` | embodiment reports completion | error | unreachable (rate-limited and aggregated so unattended motion does not flood receipts) |
| Email draft/approve/queue/cancel | `email.drafted`, `email.approved`, `email.queued` (pending), `email.cancelled` | immediate (database state) | store error | n/a |
| Email send | `email.sent`: pending while QUEUED, then completed when SMTP accepts | SMTP 250 acceptance | permanent rejection (5xx) | timeout or drop after the message was transmitted (and the draft is not re-sent blindly: it needs an idempotency check) |
| Calendar write (future) | `calendar.event_created|updated|deleted` | provider acknowledgement with the event id | provider 4xx, policy refusal | no acknowledgement within the timeout |

Destructive actions keep their text-only confirmation (ADR 0011); the receipt records the outcome after consent, it never replaces consent.

## 8. Preserving existing rules; threats considered

- Authorization, consent, the 10-minute email window, voice exclusion for destructive actions, the owner-presence rules in AGENTS.md and `require_remote_auth` are untouched; receipts are outputs.
- **Forged receipt:** a model or stored text cannot write one (the route is service-authenticated and allowlisted). **Replay or stale match:** matching is by `correlation_id` for the turn. **Claim before effect:** forced into `pending` wording. **Double send on unverified:** the dispatcher must check before retrying (a design item, not new authority). **Privacy:** receipts carry ids and labels, not content. **Receipt flood** from unattended motion: aggregate and rate-limit.
- The boundary is itself testable on disposable infrastructure: H-001, the obedient-model live-route tests, and the claim-check evaluation become its regression suite.

## 9. Phasing and decisions requested

Phases, each a separate approval: **P0** this proposal and an ADR draft; **P1** additive receipt fields and the `POST /receipts/report` route with tests (no behaviour change); **P2** hub and embodiment report robot receipts (read-only observation first); **P3** email send gets `pending/completed/failed/unverified` and the duplicate-send guard; **P4** the claim check in measure-only mode (counts unbacked claims; no change to replies); **P5** enforcement on the generic branch, with the owner's wording for corrections; **P6** calendar when a write path is approved.

Decisions: (1) the four-outcome vocabulary and append-only events; (2) core as the single receipt store with a narrow report route, against hub-local tables; (3) whether unattended robot motions get aggregated receipts at all; (4) replace the sentence or the whole reply on an unbacked claim; (5) whether `unverified` email sends should block automatic retry until the owner decides; (6) who reviews the ADR.

## 10. Review notes (2026-10-11): what to prioritise

Reviewed against the live route with an obedient fake model (`tests/test_phase44h_live_route.py`, 42 cases) and the real-model run that found H-001.

**Findings.** (1) The structural protections hold today: for 12 attack-shaped requests, in text and in voice, no store changed, no email draft or receipt appeared and the hub (so the robot) was never called, whatever the model said; deterministic handlers refuse email and bulk destructive requests in fixed text and say so by voice. (2) **A request that falls through to the model branch is answered with the model's words, and if those claim success the claim is released.** Of 12 probe requests, 7 reached the model branch (for example "put the robot in standby", "mark every task as done", "turn privacy mode on", "remove all calendar events"); the obedient model's "I have deleted all the tasks..." reached the owner each time. The real 7B did the same once (H-001). Nothing acted; the owner was told something false. (3) The prototype detector finds these with high precision on the cases tried, but free-text detection will always have gaps.

**Priority order (a revision of section 9, still a proposal; each step a separate approval).**
1. **(Implemented locally 2026-10-12, not deployed; see [phase-44h.md](phase-44h.md#unclaimed-action-boundary-local-2026-10-12).) Prevent the claim at the source, simply:** an action-shaped request that no deterministic handler claims gets a fixed reply ("I can't do that from here; here is how to do it...") instead of a model call. The qualification rules already identify action requests (`_ACTION_START` in `knowledge/qualify.py`); the same recognition can route them. This removes the whole class for those requests with no free-text judgment, and it is where most of the risk sits (7 of 12 probes).
2. **Measure before enforcing:** run the claim detector over generic-branch replies in measure-only mode (counts only, no text, same aggregate-telemetry pattern as the shadow) to learn the real rate and the false-positive rate on the owner's traffic.
3. **Then enforce on the rest:** replace an unbacked claim sentence with the fixed correction only where the detector's measured precision justifies it.
4. **Receipts for robot, email and calendar (sections 3 to 7)** matter once a path can legitimately claim such an action; today none exists in the model branch, so they follow, not precede, steps 1 to 3.
5. Decide how **negative claims** are treated ("that was not done"): they are true by construction in the no-tool branch and should be exempt, with the receipt rule applying only to success claims.

**Constraints reaffirmed.** No change to consent, trust, text-only destructive confirmation, the 10-minute email window or voice exclusion; receipts remain outputs and never inputs to authorization; nothing in this section is implemented.
