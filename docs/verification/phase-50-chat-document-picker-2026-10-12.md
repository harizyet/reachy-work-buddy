# Phase 50: chat document picker (2026-10-12)

Owner request: a persistent, per-conversation document attachment in the web chat that reuses the deployed `context_document_id` contract and document-scoped Q&A, survives a refresh, is revalidated on every turn, and adds no retrieval pipeline or schema. **Built and verified locally; NOT deployed** (production is unchanged; deploying needs a hub rebuild and the owner's approval).

## Design

* **Attachment state** is a state entry in the chat's own archive (`web_chat_turns`, a JSON column), not a message and not a new table or column: `ChatDetail.document`, written by `PUT /chats/{id}/document`. It is per conversation, absent in a new one, removed with the chat, and it does not reorder the history. Android ignores the extra fields (it parses with `ignoreUnknownKeys`) and never sees the state entry as a message.
* **The hub is the authority for a saved chat:** `POST /messages` with a `chat_id` sets the turn's `context_document_id` from the chat's attachment and ignores a client-supplied one. Each turn records the document it was answered under and its citations.
* **Core is unchanged.** It already re-checks existence, deletion, source integrity, class, project and processing state on every turn and answers with its fixed replies; the hub supplies the sensitive ceiling for a typed owner message as before. Nothing is ingested into memory or the knowledge index.
* **Web:** a picker dialog (only ready documents can be chosen), the "Answering from: <title>" indicator with Replace and Remove, an unavailable-document warning, page citations under answers and in reloaded transcripts, exclusivity with the meeting context, and the choice for a brand-new chat held until the chat is created and saved before its first message.

## Verification

* **Hub** (`test_document_library_proxy.py`, 11 tests; real core with the library on and the real worker app over a fake engine, scripted model): per-conversation attachment and replace/remove with reads in between and no history reordering; owner-only with CSRF and an owner-bound user id; every message and follow-up answered from the attached document and a client-sent other document ignored; the transcript keeps the document and pages per turn and attachment changes are not messages; replace and remove change the next answer; unprocessed attachment gets the fixed reply; a deleted document shows `available: false`, the fixed reply, no model call and can be removed; a sensitive document works for the owner session; a conversation without an attachment is unchanged; deleting the chat removes the state. **Real PostgreSQL** (`test_chat_store_postgres.py`, disposable container, removed): the state entry round trip, `available` never stored, no message, no reordering, replace, remove, delete.
* **Web** (`chat-documents.test.tsx`, 9 tests; suite 279 passed, typecheck and build clean): not offered when the library is off; picker offers only ready documents; the attachment applies to follow-ups and is saved with the new chat before the first answer in the right order with no document id in the message; replace and remove; survives a refresh with the pages in the transcript; per-conversation switching, new conversation empty, unsaved choice dropped on switching; a deleted document is shown as unavailable and removable; an attach failure is reported; literal rendering of titles.
* **Real engine, real model, real browser (labelled: not a mock):** a throwaway real hub and core with the real MinerU worker and the real local model (production vLLM loopback, about ten short requests; production core and Phase 48 not involved), headless Chromium at 1280 and 390 pixels (`e2e/chat-documents.mjs`; `documents_hub_server.py` gained an optional `E2E_LLM_BASE_URL`): two documents uploaded; a new conversation starts empty; attach, ask (the answer "Audit logs must be retained for a minimum of ninety days online and one year in archive. From pages 1, 4 of ..."), follow-up with no re-attach; page refresh keeps the attachment and the pages; a new conversation has none and ordinary chat answered normally; switching back restores the attachment; replace (the capacity question answered from the other document); remove (next message ordinary); a deleted document shown as no longer available with the fixed reply; no overflow and no console errors; 30 of 30 checks. Ruff clean; full run 3,094 passed with the known baseline failures (plus one test that pinned "no hub route mentions a document", updated for the new chat route).

## Limits

* A choice made in a brand-new chat before its first message exists only in the page (nothing to attach it to yet); it is saved when the first message creates the chat.
* One source at a time: a document and a meeting context are mutually exclusive.
* Documents page "Ask" is unchanged (still its own one-off question panel).
* Not done: deployment, the owner's own browser check, Android, and any change to how answers are retrieved (lexical page ranking inside the one document, as before).
