## Verification (owner session over HTTP against `http://localhost:8080/hub`; real worker, MinerU and local model; 26 of 28 checks passed first run, the 2 failures explained below)

* **Auth and CSRF:** unauthenticated `GET /chats` 401; login without `X-Reachy-CSRF` 403; owner login 200; attach without auth 401, without the CSRF header 403, unknown document 404, unknown chat 404.
* **Workflow:** attach; cited answer (`[title, page 1]` plus a structured citation); follow-up answered from the same document; refresh keeps the attachment and per-turn citations; a new conversation starts with no attachment; switching back keeps it; replace answers from the new document; a client-sent `context_document_id` is ignored for a saved chat (the isolation probe below proves it); remove restores ordinary chat (no citations, no document).
* **Edge cases:** deleted document keeps the attachment with `available:false` and the fixed "can't find the document" reply with no content; a still-queued document gets the fixed "still being processed" reply; a sensitive document is answered at the owner session's typed-web ceiling (existing rule, unchanged); meeting-context selection still works (title returned, no document or citations on that turn).
* **The two first-run failures, and what they are.** "New conversation does not see document A" and "client-sent id ignored" both showed an answer containing document A's content with **no citations**. A second probe used facts never stated in any earlier turn: with no attachment, or with another document attached and the client sending a different id, the document's fact (58 cables) was **never returned** and only the attached document was retrieved. So the document store, ceilings and hub authority held. The earlier content came from **core's short-term conversation history**, which is keyed by the hub session's `conversation_id`, not the web `chat_id` (the hub never sends `chat_id` to core): every web chat of the owner shares one core history, so the model can repeat or even mis-tag (it printed `[pickerprobe-beta, page 1]` and an invented "12") what it saw in earlier turns. This is pre-existing core behaviour (meeting context behaves the same) and not introduced here, but it means **"new conversation" separates the transcript and the attachment, not the model's recent memory**. Open item for the owner: either accept it or scope core's turn history per web chat (a core change, out of this rollout's scope).
