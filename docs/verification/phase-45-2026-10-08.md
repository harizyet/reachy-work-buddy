# Phase 45 verification on disposable infrastructure, 2026-10-08

Evidence for stages 45A to 45D and 45F of [Phase 45](../phase-45.md). **Nothing here ran on the homelab stack's data path**: the homelab was only read (connection inventory and a read-only request burst through the hub). Everything else ran in an isolated Docker network with a throwaway PostgreSQL (pgvector image, `max_connections` 100), throwaway secrets and a freshly migrated, empty database (so no personal data), against images built from clean worktrees of the committed code. The embedding model came from the host's cache, mounted read-only, with no network access. Limits: an empty database and synthetic writes (tasks created, edited and deleted through the hub), no meeting data, containers capped at 2 CPUs; the hub's voice warm-up fails in the isolated network (no internet) and is unrelated.

## Findings from the work (beyond the connection counts)

1. **A shared pool exposed a cross-store bug.** The LLM usage store set `conn.row_factory = dict_row` on a borrowed connection and never reset it. With one shared pool every later borrower got dict rows (tasks failed with `KeyError: 0`, the hub returned 502). Fixed with a cursor-level factory (`37cef0b`); a test fails without the fix and passes with it. Under any pooler the same leak would have been worse.
2. **Migrations do use an advisory lock** (`pg_try_advisory_lock`; my first grep missed it). It is a session-level lock, so migrations must stay on the direct path; a test pins that and fails if application code ever uses advisory locks, session-level `SET`, `LISTEN`/`NOTIFY`, temp tables or named cursors.
3. **Prepared statements are a hard requirement.** With PgBouncer's `max_prepared_statements = 0` and the driver left at its default (prepare after 5 executions), the stack failed: core never became healthy in 180 s and the hub logged 3,487 `DuplicatePreparedStatement` errors. Either `DB_PREPARE_THRESHOLD=off` (the driver never prepares) or PgBouncer 1.21+ with `max_prepared_statements > 0` works; both passed. The plan sets both.
4. **Application code runs as the PostgreSQL superuser** (`POSTGRES_USER`); a dedicated, least-privilege application role would be a worthwhile later change and is not part of this phase.
5. The core container has no volume for the Hugging Face cache, so it fetches the embedding model into its writable layer after each recreate (a 45E item).

## 45A: shared pools, direct to PostgreSQL

Commits `2e0724a` (DatabaseManager, injected pools), `930c33c` (prepare switch), `37cef0b` (row-factory fix). One pool per service process (core, hub), 1 idle and at most 8, 10 s acquisition timeout, connection check on checkout, 5 minute idle and 30 minute lifetime limits; the coding-agent service has one store and so one pool. A guard test fails if any service builds a pool outside `shared.database`. Tests: core 936 passed (7 skipped), hub 433 passed (one pre-existing failure, `test_spoken_command_text_does_not_actuate_the_robot`), coding-agent 82 passed, with the Postgres-backed suites running on a disposable server. New tests prove: every store shares one pool, 60 concurrent operations through a pool of 4 never exceed 4 backends, closing a store leaves the pool usable, shutdown leaves 0 backends, waiting is bounded (1 s timeout honoured), the pool heals after `pg_terminate_backend` on all its connections, vector registration is required and enforced, an unmigrated database fails with the migration message, and no store leaves state on a returned connection.

## 45C: compatibility matrix (through PgBouncer, transaction mode)

`tests/test_pooler_compat.py`, 6 tests, passed in both modes (prepared on with `max_prepared_statements = 100`, and prepared off): repeated statements past the driver's threshold, pgvector type registration and a vector query, `SET LOCAL hnsw.*` ending with its transaction, six concurrent outbox claimers (`FOR UPDATE SKIP LOCKED`) claiming each of 40 rows exactly once, a due reminder claimed once by eight concurrent pollers, a rolled-back transaction leaving nothing with the connection reusable, and the pool recovering after PgBouncer drops all connections (`KILL` then `RESUME`). The static rules test (no session-level `SET`, advisory locks outside migrations, `LISTEN`/`NOTIFY`, temp tables or named cursors) passes. Migrations and key rotation use the direct path (compose keeps the `migrate` job on `postgres:5432`).

## 45F: failure exercises (probe: a read and a write through the hub every 0.25 s; every acknowledged write checked against the database afterwards)

| Fault | Result |
|---|---|
| PgBouncer container restart under load | 0 errors, slowest call 1.1 s, 0 acknowledged writes missing |
| PostgreSQL container restart under load | 1 read error, slowest call 6.9 s, 82 writes acknowledged, 0 missing; no manual action |
| All backends terminated server-side under load | 0 errors, 0 missing |
| PgBouncer server pool exhausted (26 to 30 clients pin 25 server connections for 25 s) | waiting is bounded: a client that cannot get a connection fails with `query_wait_timeout` after 10 s; the hub and core saw 2 errors and a slowest call of 4 s; recovered fully after release; 0 acknowledged writes missing |
| Services started while PgBouncer was down | all three exit with code 3 and a startup failure rather than hang (a restart policy retries); healthy within 6 s once PgBouncer returned |

Not exercised: a PostgreSQL crash mid-write on the homelab, a power loss, PgBouncer behaving differently at the homelab's data volume, and the reminder and alarm loops across a pooler restart (the claim-once tests cover the SQL, not the hub's polling).

## 45B artifacts (in the repository, not deployed)

`deploy/homelab/pgbouncer/pgbouncer.ini` (transaction pooling, pool 20 plus reserve 5, `query_wait_timeout` 10 s, `max_client_conn` 300), `pgbouncer/make-userlist.sh` (writes the auth file from Postgres's own SCRAM verifier, mode 0600, gitignored), and a `pgbouncer` service in `docker-compose.yml` pinned to `edoburu/pgbouncer:v1.25.2-p0` by digest, in a `pooler` profile so a normal `up` neither starts nor needs it. The applications' `DATABASE_URL` now takes `DB_HOST` and `DB_PORT` (default `postgres` and `5432`, so nothing changes until 45E), `migrate` stays direct, and `DB_PREPARE_THRESHOLD` and `DB_POOL_MAX_SIZE` pass through. `docker compose config` validates with and without the profile. A running stack is unchanged by these edits; the next `up` will recreate core, hub and coding-agent because their environment lists changed.
