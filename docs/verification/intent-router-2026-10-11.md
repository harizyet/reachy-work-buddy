# Hybrid intent routing for natural-language reads (2026-10-11)

**Status: implemented, tested and committed locally; not deployed.** Not a numbered phase. It extends the Phase 49E task inquiry and the 44H boundary and changes no frozen artifact.

## What it does

`companion_core/intent_router.py`, reached from the last branch of `conversation_turn` in `app.py` (after every deterministic handler, the 44H boundary and the 44E selective path, which keep precedence) and from the "source named without a title" record branch ("what did I write in my note about GitLab?"). The local Qwen 7B returns one JSON object from a closed schema; the application validates it and runs one existing READ handler.

| Rule | How it is enforced |
|---|---|
| Read-only | The schema's operations are `tasks.list`, `reminders.list`, `notes.list`, `records.find`, `memory.recall`, `none`. Any other name, an extra field, a wrong type or a confidence outside 0 to 1 is rejected (`extra="forbid"`, strict types). No operation can write. |
| Deterministic first | Explicit commands, consent, named-note references, the 49E inquiry, alarms and every other handler run before the router. The 44H boundary refuses action requests before the router; the router also refuses any message `is_action_request` flags. |
| `delete my tasks` | The legacy list matchers (`is_list_query`, `is_note_list_query`, `is_reminder_list_query`) now return False for a request that changes something, so the phrase "my tasks" no longer turns it into a list. 44H's own wish pattern over-matches plain questions ("Do I currently have any tasks I need done?"), so a question opener ending in `?` is exempt from this guard only. |
| Embedded instructions | The model sees only the owner's message and classifies it; it never sees a record. A clause that changes something is refused by 44H first. The handler's access is derived from modality and channel only (`selective_answer.access_for`), so nothing in the text or the model's output widens it. A shared speaker is read nothing (`inquiry.RESTRICTED`). |
| Dates | The model has no date field. The window comes from `task_intent.time_scope` on the owner's words (today, tomorrow, this week, next week, in the persona timezone); a weekday, month, other range or two windows is a fixed limitation. Tasks have no due-date column, so they stay undated; only reminders and proposals with `due_at` are placed in a window. |
| Search phrase | Must consist of words the owner used (after dropping filler such as "notes about"). Notes and meetings are matched by plain substring under `record_reference._readable`. One match is quoted verbatim; several are listed by title; none is "I couldn't find…". |
| Memory | Same store query, reply wording and most-restrictive-privacy label as the `memory.read` handler. When nothing is remembered it falls back to the notes and meetings search (verbatim), never to a model answer. |
| Fail closed | Superseded by the grounding correction below: whether a question needs the owner's records is decided from the owner's words (`requires_records`), not by the model. If it does and no supported read answers it (model said `none`, timeout, error, malformed or invented output, low confidence, a search phrase the owner did not say, or no local model), the reply is the fixed limitation and ordinary chat is not reached. The untitled-source branch keeps its existing "couldn't establish" reply. |
| No claimed completion or provenance | Every routed sentence is built from store output. The router adds no model-written text; the existing provenance backstop still guards the ordinary chat branch. |
| Cost | A message is sent to the model only if it is read-shaped (a question mark, or a question or read word first) and either names records or has a personal-lookup cue. "Tell me a joke", statements and unrelated questions cost no extra call. A call is local-only, temperature 0, at most 120 tokens, 12 s timeout. A turn with a meeting attached is never routed. |

## Stabilisation pass (same day, before any deployment)

* **Mixed read and write** (`mixed_intent.py`, checked before the record and list handlers): a message that starts as a read and has a later clause starting with a write verb the assistant cannot perform from a chat (mark, delete, remove, clear, cancel, complete, send, email, forward, archive, share, update, ...) is not run at all. The fixed reply names the operation ("I can't mark anything from here, so I haven't made any changes, and I haven't run the read part either") and asks for the read on its own. Quoted spans and "called X" titles are removed first. Supported writes (add, set, create, remind, forget) and messages that start with a write are not touched, so 44H and the existing handlers behave as before. No multi-step execution, no new write.
* **Narrowed legacy intercepts** (`task_intent.py`, `inquiry.py`): the broad task, reminder and note patterns now also need an ownership word (my, I, our, we), and a message about the topic itself (how, why, explain, best, tips, apps, tools, manager, organise, ...) is never claimed by a regex handler or the 49E matcher. "What is a task manager?", "Which notes app is best?", "Tell me about reminders in Python", "How do I organize my tasks better?", "Are there any task management apps?" no longer list the owner's records. The explicit forms (`What are my tasks?`, `show my notes`, `Do I have any reminders?`) are unchanged and still need no model call. Ambiguous wording now reaches the router.
* **Operation-level prompt**: the router prompt describes what each read operation is FOR (open work items; set reminders; which notes exist; what notes or meetings say, decide, recommend or agree; a specific remembered fact about a person, role or contact) and uses abstract examples with placeholders, no names of people or organisations. The model narrows a search to notes or meetings only if the owner used that word (enforced in code, not trusted). `records.find` for `any` and `memory.recall` now fall back to each other's store, still existing reads only; nothing found anywhere stays "not found".
* **Latency**: how-to, explain, why, define, compare and "what is a ..." questions with no my/our/we skip the classifier; so do statements and anything not read-shaped. Model output cannot change authorization: a tool name with extra characters, an extra field, a confidence of 1 or 1e9, a "kind" the owner did not ask for, or an instruction in the owner's text widen nothing (tests cover each; a shared speaker is still read nothing).
* **Verification**: 54 router tests (new: mixed requests with processing on and off, named operations, single-intent and supported-write messages, titles containing verbs, ten unrelated questions, explicit requests still deterministic, an ambiguous phrase reaching the router, decisions, recommendations and contacts, memory fallback, no classification call for conversational questions, model-supplied extras). companion-core and reachy-hub with a disposable `pgvector` PostgreSQL: 2,661 passed, 21 skipped, the same 3 baseline failures; coding-agent-service 82 passed; ruff clean. The four frozen capture-file hashes match, the five freeze test files pass (19), and nothing under `benchmarks/`, `knowledge/`, `memory/` or `action_boundary.py` changed.
* **Real local 7B smoke** (16 paraphrases not used before, synthetic text, no stores; functional only): two contact questions routed to `memory.recall` (one of them had been answered `none` under an intermediate prompt wording), a team recommendation, a technical decision, a note about a subject, a "did anyone say" question and a "what did I decide" question to `records.find`, outstanding work, pending reminders and a to-do question to the matching list, and TCP/UDP, compound interest, an art question, cooking, weather and a Zettelkasten explanation left to chat (four of those six without a classification call; the art and cooking questions were classified `none`). Four mixed requests not in the tests were recognised by the detector. The prompt was adjusted three times during this check; it is not a measure of accuracy.

## Grounding correction (same day, before any deployment)

**Defect:** a personal-record question could get `none` from the classifier and fall through to the ordinary model, which would answer about records it had not been given. **Fix:** `intent_router.requires_records(text)` is a deterministic function of the owner's message. The model now only chooses WHICH supported read answers a question that needs evidence; it cannot decide that none is needed.

* **Needs records** (read-shaped messages only): the owner's own records by name ("my tasks", "do I have any notes"); a role or contact that belongs to them ("my Google on-prem contact", "who owns the billing service"); what the owner or team wrote, said, decided, agreed, chose or recommended ("what did we decide about ClickHouse"); what a note, memo or meeting says, mentions or is about; who attended a meeting; a record noun with a status word ("tasks that remain unfinished"); and what a named person, the team or anyone recommended, decided, said or promised ("Who did Joshua recommend?"). A question about the topic itself (how, why, explain, best, apps, tools, ...) with none of the specific cues above is general knowledge.
* **Behaviour:** needs records and a supported read is chosen: that existing handler answers from the stores under the turn's access. Needs records and anything else (including `none`, a timeout, a connection error, malformed, truncated or invented output, a confidence below 0.75, a search phrase containing a word the owner did not say, or no local model configured): `CANNOT_PLACE`, a fixed clarification that says nothing was looked up and nothing is guessed, and suggests naming the record or asking a general question. Does not need records: unchanged (classifier only when the gate says so; `none`, failure or timeout means ordinary chat). Statements never need records.
* **Precedence unchanged:** slash commands, named-note references, the 49E inquiry, 44H, the mixed-intent refusal, an attached meeting (answered from that meeting) and the 44E selective path all run before this check. Routing text comes only from the owner's message; note content is never given to the classifier, so it cannot change routing, and a model-supplied operation name, kind, confidence or query cannot widen access.
* **Two strictness fixes found by the live check** (the model chose the right operation both times and the validation refused it): `kind` is advisory (an unknown value such as `"contact"` is treated as `any`; the owner's words decide in code), and a search phrase is accepted if each word is one the owner used or differs from one only in its ending ("recommended" for "recommend"), and is then replaced by the owner's own spelling. The operation name is still a strict closed set.
* **Existing tests changed on purpose:** six tests in `test_selective_answering*.py`, `test_selective_shadow*.py` and `test_knowledge_shadow_route.py` used "Who owns the Quill message queue?" (and similar) as their example of the ordinary-model path; they now expect the limitation for those questions, and the counts of model-answered turns follow. Their purpose (parity, isolation, no leak) is unchanged.
* **Verification:** 131 router tests, including every case you listed (Joshua, ClickHouse, Google on-prem contact, tasks next week, task manager, databases, router `none`, timeout and malformed JSON for each of twelve records questions across six failure kinds, an ambiguous owner question, injection text, poisoned note content, a titled-note reference, a shared speaker, 44H and mixed precedence). companion-core and reachy-hub on a disposable `pgvector` database: 2,738 passed, 21 skipped, the same 3 baseline failures; coding-agent-service 82 passed; ruff clean; the four capture-file hashes match, the five freeze test files pass, and nothing under `benchmarks/`, `knowledge/`, `memory/` or `action_boundary.py` changed. Real local 7B, 16 questions (functional only): every question that needs records either routed to a supported read or would have received the limitation, none to ordinary chat; general questions (telephone, CEO, weather, learning Rust, task manager, databases) reached chat, and the four that were obviously conversational cost no classifier call.

## Rollout control: `INTENT_ROUTER_ENABLED` (added before any deployment)

The router had no switch of its own, so deploying it would have activated it at once. `INTENT_ROUTER_ENABLED` (default `false` in code, read once at startup, and passed by `deploy/homelab/docker-compose.yml` to companion-core only) now gates exactly the model-driven part:

| | Flag OFF (default) | Flag ON |
|---|---|---|
| Classifier model call | never | only for eligible requests (read-shaped, records cues or personal-lookup cues, not general how-to, not action, not mixed, no meeting attached) |
| Records-grounding clarification (`CANNOT_PLACE`) | never produced; a records question the deterministic chain does not claim reaches ordinary chat as it did before the router | produced when a question needs the owner's records and no supported read answers it |
| Untitled-source note question ("in my note about GitLab") | the pre-router "couldn't establish" reply, no model call | routed, or the same reply |
| Matcher narrowing, mixed read/write refusal, 44H, named-note precedence, deterministic handlers | active | active |
| Writes | none introduced | none introduced |

Tests (`tests/test_intent_router.py`, 150, run in both states): flag parsing and the Compose default; flag OFF never calls the router model, even with a valid route scripted; flag ON calls it exactly for the eligible questions and for none of the general or deterministic ones; the deterministic handlers, named-note precedence, mixed refusals, 44H and the narrowed matchers behave identically in both states (one test replays the same eight messages under both and requires identical replies); malformed or unauthorised routing leaks nothing in either state; no record is created, changed or completed. The five shadow and selective test files edited during the grounding correction were restored to their pre-router form, because under the default-OFF flag they run the pre-router behaviour and pass unchanged. Suites on a disposable `pgvector` PostgreSQL: companion-core and reachy-hub 2,757 passed, 21 skipped, the same 3 baseline failures; coding-agent-service 82 passed; ruff clean; the four capture-file hashes match, the five freeze test files pass, and nothing under `benchmarks/`, `knowledge/`, `memory/` or `action_boundary.py` changed.

## Follow-up work (not deployment blockers: none produces an unsupported factual answer)

* **Substring search.** `records.find` and `memory.recall` match a plain substring, so a model phrase that is not contiguous in the stored text finds nothing and says so. A better matcher (word-level, stemmed) would be a new retrieval capability and was not added.
* **Title matching.** A note whose title itself contains a write verb cannot be read by title (`record_reference.parse` refuses it through 44H's check, as before). "What notes have I got about Harbor?" lists every title because the explicit notes list ignores the subject.
* **Unmarked work-knowledge questions.** A question with no cue at all ("How many retries before a failed Harbor job is parked?") is indistinguishable from general knowledge by wording and still reaches ordinary chat when the 44E selective path is off. The existing provenance backstop and the 44E answerer are the controls for that; widening the cue list further would block general questions.
* **Ambiguous named-actor questions.** "Who did Obama recommend for the post?" is treated as a records lookup (clarification or "not found"), because the shape matches "Who did Joshua recommend?". A verb outside the cue list ("endorse") is not recognised.
* Phrase list maintenance: the cue lists are fixed patterns and will need occasional additions.

## Known residuals

* A mixed request whose write verb is not in the closed list, or whose read half does not open the message ("Delete the old ones and show the rest" is 44H's, the rest depends on the verb), is not recognised by `mixed_intent`; the verb list is deliberately conservative and 44H is unchanged.
* "What notes have I got about Harbor?" still lists every note title (an owned, explicit notes question; the subject is ignored). It is truthful but not filtered.
* Memory and note matching are substring tests, so a model query worded differently from the stored text finds nothing and says so. The prompt now asks for one word or a short consecutive run, which helps but does not guarantee a hit; the live check showed some poor queries (for example "settle").
* A note whose title itself contains a write verb cannot be read by title: `record_reference.parse` refuses it through 44H's check, as it did before this work.
* Questions with an ownership word and a records noun that the model answers `none` go to ordinary chat; the existing provenance backstop is the only guard there.
* A records question while the local model is down or slow gets the fail-closed reply instead of an ordinary chat answer (by design); a router timeout adds up to 12 s to such a turn.
* Deployment is a core recreate, which starts a new Phase 48 cohort boundary. Not done.
