Playwright stability: two earlier runs each had one failure caused by the test, not the app. The hub re-sets the session cookie on every response, so an in-flight request brought back a cookie the test had just cleared. The expiry-on-reload test now waits for network idle, and the polling test answers `/status` with a 401 through `page.route` instead of clearing cookies. After that, three consecutive full runs passed 30 of 30.

## What the browser tests cover

Redirect to sign-in with no private text in the DOM; wrong password refused with the server message; sign-in shows the real `/status`; reload keeps the session; logout then back-navigation and a fresh load show nothing private and the server really answers 401; cleared cookie returns to sign-in on reload; a 401 during polling (cookie cleared mid-session) returns to sign-in with the "session has ended" notice and removes private text; nothing in localStorage or sessionStorage; no horizontal overflow on mobile; the legacy `/ui/` and `/app/` still serve. Each runs at both viewports and both mounts.

## API compatibility

Checked against the real hub app's OpenAPI document and live responses, not assumed. `/auth/me`, `/auth/login`, `/auth/logout` and `/status` return bare `dict`, so OpenAPI has no response fields; the client's types and parsers are hand-written and validated against a real response sample (`clients/web/src/api/samples.json`), and `test_web_client.py` fails if the hub's response shapes or those four OpenAPI operations change. Contract points reproduced from the legacy client: relative base path (`hubBase`), `X-Reachy-CSRF: 1` on every request, same-origin credentials, `no-store`, `detail` error text with a status fallback for non-JSON gateway failures, 401 to sign-in. `/auth/login` and `/auth/me` 401s are expected and do not trigger the session-expired path.
