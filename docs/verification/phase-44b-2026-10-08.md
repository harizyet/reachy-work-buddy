## What the tests establish

- **Adapters** describe each store with its classification, scope, validity and provenance; meeting text is the owner's accepted correction with the speaker's name, never the raw transcript (which the test confirms is untouched); summaries and minutes are marked model-written at confidence 0.5; forgotten, expired, missing, cancelled and untranscribed sources produce no items and say which; the version hash is stable and changes with the text, the classification and the scope.
- **Worker** indexes new text once and a repeat changes nothing; embeds only changed parts (one corrected segment of six, then all six when a speaker is renamed); removes parts and whole sources that disappear; restores a forgotten memory when it is restored; embeds off the event-loop thread in batches of at most 16; re-embeds once when the embedding model changes; survives one bad source; backs off 1, 2, 4... minutes up to an hour, sets a row aside after 8 failures and revives it on a new change; never modifies a store.
- **Outbox**: duplicates collapse to one row per source; a crashed worker's claim is retried after its lease and not before; a change that arrives during a sync is not deleted by that sync's completion (the generation guard), on both the in-memory and Postgres implementations; 24 sources worked by two concurrent workers are each synced exactly once.
- **Triggers** (Postgres): an insert, update or delete queues the source in the same transaction; a rolled-back change leaves no event; repeated updates coalesce into one row with a higher generation; reads that stamp `last_accessed` or `notified_at` queue nothing; forgetting a memory, deleting a note, task, reminder or meeting, cancelling a meeting and deleting a document chunk remove the index rows **before any worker runs**; restoring a forgotten memory queues it again.
- **Reconciliation** repairs a deleted row, a stale version, an orphan, an expired memory and a completely empty index (as after a restore), and a second pass finds nothing.
- **Revalidation** with the index deliberately stale: a forgotten, deleted, expired, cancelled or emptied source is never returned (one test per case); the text returned is the source's current text, not the indexed copy; a reclassification the index has not seen still applies, and an index copy that is stricter than the source wins; scope, cloud destination and sensitivity ceiling are applied to what survives; historical mode, unknown parts, unknown types and repeated candidates behave; each source is read once however many of its parts are candidates; the same against a stale Postgres index on the real stores. Mutation check: breaking the module in three ways (skipping the visibility check, trusting the index label, never applying the access context) makes 2, 3 and 2 tests fail respectively.
- **Migration 027**: applies to a seeded 026 database and queues the existing records; is idempotent; rejects an invalid classification; can be undone by `alembic downgrade` and by `deploy/homelab/rollback-027.sql` (both leave the authoritative rows intact, remove the triggers, and let 027 be applied again); applies cleanly over leftovers from an earlier copy. The 026 recovery test (dump at 025, upgrade, restore) now follows the new recovery order and passes.
- **Switching on**: the flag parser (`true`, `1`, `yes`, `on`; anything else is off); an app built with injected in-memory stores never starts the indexer even with the flag on; the background loop reconciles at start, indexes a new note and removes a deleted one on Postgres, and stops on cancellation.

## Problems found by the tests and fixed

1. The worker loop suppressed cancellation while sleeping, so it could never be stopped (the loop test hung). Fixed; cancellation now propagates.
2. After 027 exists, `pg_restore --clean` of an older dump fails because the new `embedding` column depends on the vector type. The recovery procedure is now: run `rollback-027.sql`, then restore. The 026 recovery test was updated to follow it.
3. Opening the Postgres stores in a fixture and using them in other event loops hung; the stores now open inside each test's own loop, as the other durability tests do.

## Embedding load

`benchmarks/knowledge_retrieval/indexing_load.py`, real all-MiniLM-L6-v2, 400 synthetic segments embedded as the worker does (batches of 16 on a worker thread), with an event-loop ticker standing in for chat and voice handling in the same process. Development host, 20 CPUs, load average about 2.

| torch threads | time for 400 segments | segments per second | worst event-loop stall while embedding |
|---|---|---|---|
| 14 (torch's default) | 1.98 s | 202 | 1.6 ms |
| 2 | 1.03 s | 388 | 1.8 ms |

The event loop is not blocked either way, and 2 threads were faster here (the default oversubscribes the host). Core therefore sets 2 threads for indexing (`KNOWLEDGE_EMBED_THREADS`). **Not measured:** the effect on the speech, language-model and diarization services that share the homelab's CPUs, and a real voice turn during an index build; that needs a deployment, and a first full build of the existing records is small (about ten records today).
