# Phase 44F: implementation slices (preparation only; not authorized, not started), 2026-10-11, updated 2026-10-12

Source design: [Phase 44 section 3.1 and 3.1a](phase-44.md#31-44f-conversational-memory-capture-roadmap-2026-10-08-plan-only) (candidates are not memory; selection mechanisms order and suggest, never accept). This page cuts it into slices that can be built, tested and reviewed one at a time. **No code and no migration exists for any of them.** Owner decision, 2026-10-12: the curiosity definition is **accepted** with three categories (below). Phase 44F is still not to be implemented.

## Rules that apply to every slice

Casual conversation never becomes authoritative memory without the owner's explicit accept. Local-only. Privacy mode, shared and non-private channels, sensitive turns, assistant text and retrieved or attached content produce no candidates. Everything is behind its own flag, off by default, with a per-slice owner approval. Receipts for every accepted write. No change to consent, trust or the text-only destructive-confirmation rules. Tests on disposable infrastructure, including live-route injection cases (a planted instruction cannot create a candidate, change its priority or accept it).

| **8** | Curiosity evaluation | **Accepted definition (owner, 2026-10-12): curiosity is Reachy suggesting a question the owner can answer or dismiss, in three categories.** (1) *Clarifying curiosity*: a question that resolves an ambiguity or a gap that blocks a good answer ("You said Dana owns security reviews; who owns rotating the Quill credentials?"). (2) *Personal curiosity*: an interest in the owner's preferences and context that makes later help better ("Do you prefer written summaries or a quick spoken one?"). (3) *Continuity curiosity*: a question that closes a loop from earlier ("Did the Lantern review happen on the 14th?"). Rules for all three: **private channel only where appropriate** (never a shared speaker, never a sensitive turn, never in privacy mode), **rate-capped** (a hard daily and weekly cap), **dismissible** (one tap or "not now", with a "never ask about this" suppression), quiet when the owner is busy (existing interruption policy), and **never itself an action**: a curiosity prompt cannot change a record, send anything or move the robot. **An answer may produce a memory candidate but never durable memory automatically.** The only path is: *curiosity → conversation → candidate → governance/review → durable memory*; the candidate enters slice 1's store as `pending` with provenance "answer to curiosity prompt <id>", is shown in slice 3's review surface, and only the owner's explicit accept calls `add_memory` and writes a receipt. Evaluate each category separately by usefulness against annoyance on the owner's ratings, with the hard cap and an off switch. | 3, 5 | Owner-rated usefulness per category; prompts per week under the cap; dismissal rate; zero prompts from sensitive, shared or privacy-mode contexts; zero memory rows created without an accept (table comparison); a planted instruction cannot create, prioritise or accept a candidate; the prompt text is generated from code templates or reviewed rules, not free model text, until a separate evaluation allows it |
| **9** | Re-entry priority | When an accepted memory or pending candidate is surfaced again for confirmation ("still true?"); a queue and notification, never injected into a prompt. | 4, 5 | Share found useful; weekly cap |

## Suggested order and review points

0, 1, 2, 3 form the first usable milestone (a reviewed, owner-controlled candidate queue from deterministic rules); 4 is the second; 5 to 7 and 9 are selection and presentation upgrades judged on owner-reviewed data; 8 is last and optional (its three categories can be enabled one at a time). Each slice ends with a dated verification record and an owner decision before the next begins.
