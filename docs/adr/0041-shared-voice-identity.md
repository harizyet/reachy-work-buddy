# ADR 0041: Shared voice identity (phone-first)

- Status: **Accepted for isolated implementation 2026-10-15** (owner decisions at gate G0, [Phase 32](../phase-32.md)). Built on a feature branch, not merged or deployed. Amends [ADR 0038](0038-meeting-speaker-identification.md) (see its amendment). Builds on [ADR 0024](0024-owner-recognition-trust.md), [ADR 0011](0011-destructive-action-consent.md), [ADR 0025](0025-speech-inference-service.md), [ADR 0029](0029-android-companion-app.md).
- Date: 2026-10-15

## Context

Phase 25 defined owner-voice evidence for the robot only: `SpeakerVerifier` takes a robot id, a robot voice session and monotonic times, and has no implementation. The owner wants the phone to be the first place voice identity works and the same enrolled identity to serve meetings later, with the robot deferred. Android's `SpeechRecognizer` returns text, not audio, so the phone cannot supply evidence today. The [32A.0 inventory](../verification/phase-32a0-inventory-2026-10-15.md) records the code facts this ADR relies on.

## Decision

1. **Identity evidence, never authority.** A voice result is `VoiceEvidence` for one utterance, returned to the session that sent the audio. It does not set a trust level, raise a privacy ceiling, approve an action, end a login or reach Companion Core. A spoken turn is still a voice-modality message: ADR 0011's text-only confirmations hold for a verified owner. A missing, uncertain, failed or negative result changes nothing about what the signed-in owner may do.
2. **One capture path.** A client records one mono 16 kHz PCM16 WAV per utterance and uploads it once (`POST /voice-identity/turn`). The hub's existing STT and the verifier read those same bytes concurrently; the conversation then runs as an ordinary `web`/`voice` message. Enrollment samples use the same format and the same embedding call. There is no second microphone path, no continuous listening, and the existing text `/messages` and meeting-recording flows are unchanged. Meeting matching (32A.M) reads the stored meeting recording and the diarization that already exist.
3. **A stateless `speaker` service computes embeddings; the hub decides.** SpeechBrain ECAPA-TDNN (the model measured in [Phase 25a.1](../verification/phase-25a1-voice-benchmark-2026-09-28.md)) runs on CPU in a profile-gated sidecar following ADR 0025's pattern (`deploy/homelab/speaker/`, shared `SPEECH_SERVICE_TOKEN`, a `/data` volume for the pinned model). It keeps no audio or embedding and never learns whose voice it heard. The hub owns profiles, consent, thresholds, quality rules, evidence and expiry. The hub image stays free of torch. GPU acceleration is out of scope until CPU latency is measured on the homelab and found wanting.
4. **Transport-neutral evidence.** `shared/models/voice_identity.py` adds `VoiceEvidence` with client kind (`android`/`web`/`robot`), client id, device id, auth session id (None until server-side sessions exist, then required), utterance id, model and calibration versions, profile id/version, quality reasons and a four-valued state (`verified`, `uncertain`, `not_verified`, `unavailable`). `to_speaker_evidence()` projects it onto the robot's `SpeakerEvidence`, so the robot interfaces are unchanged and `NoSpeakerVerifier` stays the robot default. Evidence lives in a process-local ledger with a 10 s lifetime, keyed by owner and client, valid only for its own utterance and session, replaced by the next turn, and cleared on re-enrollment or deletion. The API returns the state and an expiry, never the similarity score or any vector; `replay_protection` is always `"none"` and `spoof_check` is `"unavailable"` because no anti-spoof model exists.
5. **Encrypted, versioned profiles in the existing database.** Migration `038_voice_profiles` adds `voice_profiles`. The template (the mean unit embedding of the enrollment samples) is stored only as AES-GCM ciphertext under a key in the existing keyring file (`SECRET_KEY_FILE`, outside Postgres), with the profile id, owner and model version as authenticated data, so a copied or relabelled row does not decrypt. A profile has a `version` (incremented on replacement), `model_version`, consent time and the enrolling client's provenance. There is at most one owner profile; re-enrolling replaces it in place and deletion removes the row. A model change makes old profiles unusable until re-enrollment (reported as `model_changed_reenroll`), never silently reinterpreted. Limits: dead Postgres tuples persist until vacuum, and a database backup holds the ciphertext; deleting a profile does not reach backups, which stay unreadable without the key. Key rotation does not re-encrypt profiles yet.
6. **Enrollment is explicit.** Drafts hold embeddings in hub process memory only (15-minute lifetime, 12 samples, lost on restart). Commit needs an owner cookie session, CSRF, a fresh reauthentication (the existing `/owner-recognition/reauth` window), an explicit consent flag, at least five usable samples from one model version, and mutual consistency (each sample against the mean of the others) so two voices cannot be enrolled together. Delete needs the same reauthentication. The routes accept the owner cookie only, never the `REMOTE_UI_TOKEN` bearer.
7. **No calibration is shipped.** Until the owner approves thresholds after the GV benchmark (`tools/voice_identity_benchmark.py`), nothing can be `verified`: results are `unavailable` with reason `not_calibrated`. The feature is off by default (`VOICE_IDENTITY_ENABLED=false`) and the routes 404 when off. Quality failures (too little speech, too quiet, clipped) give `uncertain`; service, storage, key or model problems give `unavailable`; none raises.
8. **Meeting identification (32A.M, designed here, not built).** The same embedding service and model version compare each diarized cluster's clean sample windows (the windows [ADR 0038](0038-meeting-speaker-identification.md) already chooses) with consented profiles only, with an explicit unknown outcome and a threshold calibrated separately from live verification. Suggestions are stored apart from `meetings.speaker_identity`, are never applied automatically, and the owner confirms, renames, rejects, marks Unknown or skips exactly as in ADR 0038. Embeddings for a meeting are computed on request and not persisted. A typed speaker name is not consent; a profile for anyone but the owner needs a separate explicit consent-and-enroll action; nobody is enrolled from a meeting automatically.
9. **Server-side, per-device revocable sessions (32A.1 design, approved, not built).** Replace the stateless signed cookie's meaning with a session id: an `owner_sessions` table (id, device label, created, last seen, revoked at), the cookie carrying only the id, `require_remote_auth`/`require_owner_session` checking it, the 12-hour idle expiry kept, logout and an owner "sign out device" action revoking one row, and a password change revoking the others. Voice evidence binds to this session id once it exists. This changes production sessions and is a separate approval gate.
10. **Transport stays HTTP (owner decision, amended 2026-10-15).** Phase 32A adds no TLS, certificates, reverse proxy or HTTPS migration; the app keeps its cleartext allowance and the tailnet remains the intended path. HTTPS is a separate future hardening task. Consequences are listed below and in the threat table.
11. **Robot untouched.** No robot microphone, camera, direction or fusion work; `ROBOT_VOICE_ELIGIBLE = False` and the robot sensitivity gate stay as they are.

## Threat model (transport-focused)

| Exposure | State under HTTP | Mitigation / limit |
|---|---|---|
| Session cookie and voice audio on the phone-to-hub hop | Plaintext unless the path is the tailnet (WireGuard) | Use the tailnet address; on a plain LAN cookie, audio, transcript and the evidence state are readable by anyone on the segment. Not fixed in 32A |
| Hub to speaker service, hub to core | Plain HTTP on the Compose network, token-checked only on the speaker service | The speaker service publishes no host port (tested); a host with a hostile container on that network is out of scope |
| Voice routes on the one public-capable Caddy port | `/hub/*` proxies every hub path, so the routes exist wherever the hub is reachable | Owner cookie session, CSRF, reauthentication for profile changes, 404 when disabled; the Caddy file's existing warning stands: never expose this port to the Internet |
| Raw audio or an embedding in logs, prompts, RAG, telemetry | None written; embeddings only in process memory (drafts), the speaker service, and ciphertext at rest | Tested that responses carry no score or vector; log lines carry versions and counts only |
| Stolen cookie | Valid up to 12 h idle, no revoke (until decision 9 ships) | Does not pass reauthentication for profile changes |
| Replay or synthetic owner voice | Not detected | `verified` carries no spoof claim; GV measures what was tried |
| Voice mismatch used to lock the owner out | Not possible: no code path ends a session on a result | Tested |

## Android client (Phase 32A.V, added 2026-10-15)

- **One capture class.** `PcmCapture` (`VoiceCapture.kt`) records one utterance as mono 16 kHz PCM16 in memory (`AudioRecord`, `VOICE_RECOGNITION` source), ends it with an energy endpointer (`Endpointer`, tested on the JVM), and yields a WAV. It is the only new microphone consumer; nothing is written to disk or logged, and the buffer is zeroed after use. It has the same shape as `SpeechInput`, so Talk's voice loop is unchanged.
- **When it is used.** Voice mode uses it only when the hub reports `enabled` and the owner has not switched on "Use this phone's speech recognition" (`Prefs.phoneRecognizer`, default off). Otherwise the phone's `SpeechRecognizer` runs exactly as in 0.19.0. The owner can always fall back to it if the hub's recogniser is down.
- **One upload, then the old path.** The clip goes to `POST /voice-identity/turn?converse=false`: the hub transcribes and checks the speaker from the same bytes and returns the transcript and a state; the app then sends the text through the unchanged `/messages` path as a voice-modality message. So "begin meeting recording" is still matched on the phone and never reaches the conversation, ADR 0011 confirmation rules and the spoken privacy ceiling are exactly as before, and a failed or missing speaker check cannot stop a conversation. The server's `converse` default (true) remains for other clients.
- **Display.** `ownerMatch()` words the result: before calibration nothing is ever shown as verified (a `verified` from an uncalibrated hub is shown as "unverified"; poor clips as "inconclusive"). The line is shown for the result's lifetime (about ten seconds) and is not stored. No code reads a result to enable, hide or change anything.
- **Enrolment UI.** Menu → Voice identity: progress to five good clips, per-clip quality and delete, cancel (drops the hub's draft), a consent statement, password re-entry on save, test, delete. The microphone is single-use, so recording is refused while a meeting recording runs.
- **GV workflow.** The evaluation screen uploads labelled clips (`X-Reachy-Benchmark-Label: role=…;speaker=…;condition=…`) to the existing owner-recognition benchmark store (explicit opt-in, encrypted at rest, deleted from the same screen); `tools/voice_identity_benchmark.py` computes error rates and threshold candidates off the phone. Replay and synthetic probes are attacks whoever they claim to be. No threshold is chosen by the phone or the tool.
- **Identity.** The install id (a random UUID in preferences) and the device model are sent as provenance. They are asserted by the client and are not authentication.

## Consequences

- Schema head moves to `038_voice_profiles` (`rollback-038.sql` drops enrolled profiles; the migration is additive and repeatable over a leftover copy). A deploy is the usual backup, then core, hub and coding-agent together; the `speaker` profile and `VOICE_IDENTITY_ENABLED` are separate switches.
- A phone voice turn becomes an audio upload in 32A.V's Android slice. Until that slice exists the server routes can be driven only by tests and tooling.
- ADR 0038's "no embedding is computed" is relaxed for consented profiles only (its amendment).
- Phone-calibrated numbers do not transfer to the robot; 32B recalibrates.

## Alternatives considered

- **Run the model inside the hub.** Adds torch to a transport/auth service and ties inference restarts to sessions (the ADR 0025 argument).
- **Keep Android STT and record a second stream for the verifier.** Two microphone consumers, microphone contention on the phone, and speech locality left unknown.
- **Store templates as pgvector rows.** Plaintext embeddings in the database; the 1:1 case needs no similarity index.
- **GPU first.** No evidence it is needed; CPU 3 s clips took about 0.36 s on the dev box.
