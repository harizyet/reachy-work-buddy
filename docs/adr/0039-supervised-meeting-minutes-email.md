# ADR 0039: Supervised meeting-minutes email through a dedicated sender

- Status: **Proposed 2026-10-14** for [Phase 55](../phase-55.md). Builds on [ADR 0011](0011-destructive-action-consent.md), [ADR 0020](0020-schema-and-secrets.md), [ADR 0032](0032-meeting-outputs-and-context.md) and [ADR 0038](0038-meeting-speaker-identification.md).
- Date: 2026-10-14

## Context

The owner wants Reachy to email the summary and minutes of a finished meeting from a dedicated account, each message reviewed and approved by the owner. ADR 0011 already fixes the contract (approval and send are text-only; a send waits ten minutes and can be undone; the dispatch loop is the only sender), ADR 0020 where credentials live, and ADR 0038 makes speaker names the owner's statement. The existing implementation could not carry this: its sender wrote a raw string (no MIME, one recipient, unsanitised headers) and its loop could send twice or retry a message the server had already accepted (see [the audit](../phase-55.md#stage-a-architecture-and-integration-audit)).

## Decision

1. **One outbox, one loop, one sender.** The package is an `EmailDraft` of kind `meeting_minutes` (additive columns on `email_drafts`, migration 036). `email/workflow.py`'s loop stays the only code that sends; `MailSender` is the only sender it calls. No second queue.
2. **States.** `DRAFT, READY_FOR_REVIEW, APPROVED, QUEUED, SENDING, SENT` plus `CANCELLED, FAILED, UNKNOWN_DELIVERY`. Cancelling a queued message returns it to `APPROVED` (ADR 0011's undo is unchanged); discarding ends it as `CANCELLED`.
3. **Approval is bound to a hash of the exact package** (kind, sender, complete To/Cc/Bcc, subject, body, each attachment's SHA-256 and size, the source revision). The owner approves by typing `SEND` against the hash they saw. Any edit recomputes the hash, returns the message to review and clears the approval; a changed meeting (regenerated outputs, renamed speakers) blocks queueing until the message is refreshed and reviewed. At dispatch the loop re-derives the hash from the stored rows and verifies every attachment; a mismatch fails the message and sends nothing. **Nothing is regenerated at dispatch.**
4. **Text-only, owner-session-only consent.** Approve, queue and settle go through `require_text` and are reachable only through the hub's owner-session routes (no bearer, CSRF). The older conversational "send/approve draft" handlers are restricted to plain text drafts, so a package can never be approved or queued from chat or voice. A conversation may only **prepare** a draft (no recipients, nothing sent).
5. **Delivery outcomes are typed, and ambiguity is never retried.** The sender raises `SendRefused` (nothing delivered, final: bad credentials, refused recipient, 5xx, disabled sender, changed identity), `SendTransient` (nothing delivered, may work later: cannot connect, 4xx before acceptance), or `SendUnknown` (the server may have the message). Claims are atomic (`UPDATE … FOR UPDATE SKIP LOCKED`); transient failures retry up to three times with backoff; `UNKNOWN_DELIVERY`, and any `SENDING` row found at start-up, is left for the owner to settle ("it arrived" or "send it again", which needs a fresh approval and a new Message-ID).
6. **Dedicated Gmail sender over SMTP.** `smtp.gmail.com:587` with STARTTLS and an app password on a dedicated 2-Step-Verified account needs no new Google grant, so it is the implemented path. The credential is stored only in the SecretStore (`owner/mail-sender/password`), is write-only in every API, and never appears in a settings row, response, event or log. TLS is always negotiated by us with certificate verification (the library's automatic upgrade is disabled) before a credential is sent; an authenticated sender with `security: none` is refused. The sender identity is enforced: Gmail must sign in as the address it sends as, a draft's approved sender must still match at dispatch, and a meeting package never falls back to the deployment's `SMTP_*` environment. **External delivery is off by default** (`MEETING_EMAIL_ENABLED` false: no routes, no service; and the sender's own `enabled` false until the owner has verified the connection and switched it on; any change to the sender or its credential switches it off again). Verification signs in and quits: no message, no recipient. The read-only Gmail OAuth grant (ADR 0021) is untouched. **Alternative:** a separate send-only OAuth grant (`gmail.send`) with the same MIME bytes; not built.
7. **Content rules.** Only what the owner can already see: title, date and time zone, participant names, the stored summary and minutes (refused if they predate the current speaker names), decisions with their evidence and an honest label (they are never individually confirmed), and only owner-confirmed actions. Pending, dismissed or out-of-date findings, the recording, the raw transcript and internal analysis are never included. A sensitive meeting needs an explicit acknowledgement that is recorded in the approved source.
8. **Recipients are the owner's choice.** Manual entry, saved owner-approved groups, and calendar-invitee suggestions that are offered unchecked from the single nearest calendar event. Nothing emails speakers or attendees automatically; addresses are validated strictly (no display names, quoting or control characters; at most 20 per message; Bcc is an envelope recipient only).
9. **PDF.** A deterministic stdlib writer (Courier, WinAnsi) makes the attachment at preparation time; text it cannot encode fails the PDF with a clear message and the message can go without it. A richer layout needs a PDF library and a lockfile change and is a later decision.

## Addendum (2026-10-14): the sender test

The owner asked for a way to test the account from Settings with a textbox for the recipient. **Decision:** `POST /meeting-email/sender/test {to}` sends ONE fixed message ("Reachy test email": a short note naming the sender and the time, no meeting content, no attachment) to the single address typed. Safeguards: owner session and CSRF through the hub (never the bearer), text-only (`require_text`), exactly one validated address (no list, no Cc/Bcc), the sender must be **configured, verified and switched on** (so "off" really means off; a test is never a way around it), at most 5 an hour with a 10-second gap, and no fallback to the deployment's `SMTP_*` environment. It is not a side door: it is a stored `sender_test` draft with the same package hash, approval record, atomic claim, integrity check and outcome handling, recorded in the same event history, sent by the same code path (`dispatch_due_drafts`). **One deliberate exception to ADR 0011's ten-minute window:** the test is sent immediately, because the owner is waiting for the answer, its content is fixed and non-sensitive, and it can reach only the address the owner has just typed; waiting ten minutes would defeat a connection test. It is never reachable from conversation (no matcher), cannot be opened, edited or approved through the meeting routes (they 404 for it), and meeting messages cannot be sent through it. Failure and ambiguity are reported to the owner as they are (`failed`, `unknown_delivery`) and not retried.

## Consequences

- Migration `036_meeting_email` (`rollback-036.sql` deletes meeting drafts, attachments, history, sender settings, groups and the stored credential; plain drafts and meetings are untouched). Deploying means backup, then core + hub + coding-agent together.
- The older text-draft path gained header-injection protection, atomic claims and failure states; an unauthenticated, plain relay (Mailpit, a campus relay) keeps working for text drafts as before.
- Pre-existing conversational drafts to a non-address recipient now fail instead of being sent with a malformed header.
- Only an owner can turn sending on, and only after a verified connection; the first real message must go to an owner-controlled test address.
